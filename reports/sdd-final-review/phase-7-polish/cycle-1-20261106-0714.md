## Tech Leader Verdict

### Architecture Assessment
Alinhamento com os ADRs bom: dispatcher com 4 especialistas como tools (ADR-0004), cada nó um `create_agent` (ADR-0003), checkpointer local (ADR-0001), SQL parametrizado em conexão somente leitura (ADR-0002). SOLID aceitável para o escopo. Uma lacuna estrutural real: `_run` em `agent/graph.py` não tem fronteira de erro. É o único achado que pode quebrar a sessão de um avaliador. Reconstruir grafo e saver por requisição é desperdício inofensivo para um protótipo de um usuário: documentar, não corrigir. A fronteira de confiança das tools de pedidos (ID aceito sem vínculo, busca por substring) é risco aceito para um protótipo local, mas o README descreve de forma diferente do que a tool faz.

### ADR Compliance
- ✅ ADR-0001 a ADR-0008: compatíveis. ADR-0006 tem dois detalhes aquém do texto (o `chmod 0600` roda depois do `write_text`).
- 📝 Novo ADR: nenhum. Acrescentar nota nas Consequências do ADR-0004 (falha de especialista deve virar resultado de tool, não exceção) e uma limitação no README (`customer_id` não vinculado ao cliente identificado).

### Learning Lessons Applied
- ✅ LL-0001: aplicada (cosseno, título embutido, calibração empírica).
- ✅ LL-0002 (avaliar ponta a ponta): aplicada.
- ❌ LL-0002, outra metade (testar o caminho como ele roda): parcialmente não aplicada. A bateria usa `graph.ainvoke` e nunca passa por `stream_reply`, `respond` ou `submit_key`, justamente onde estão os bugs MEDIUM do QA. Correção pequena: um teste com grafo falso para `respond` e outro para `submit_key`.

### Cross-Report Synthesis
Sistêmico: (1) bordas sem teste: UI, falha e validação de entrada, ou seja, ausência de contrato de falha entre as camadas; (2) autorização só no prompt: IDOR, enumeração e troca de chave são o mesmo padrão (tool e endpoint confiam em quem chama), aceito para protótipo, mas o README precisa descrever com precisão; (3) documentação desalinhada da medição: "37 de 37" contra 43 coletados, "passou integralmente na última rodada" contra 41/43, e a descrição da identificação. Esta é a categoria de maior prioridade, pois afeta a credibilidade diante de um revisor. Isolados: CVEs de Pillow e chromadb (não alcançáveis), container root, `.gitignore`, modo do `.env`, `_finish_tool_blocks`, promoção duplicada latente.

Caminho do avaliador (clone, `docker compose up --build`, chave, chat): funciona como o README diz; os únicos riscos são `launch()` tratando falha de rede como chave inválida, traceback cru se os embeddings falharem na partida, e falha de especialista por rate limit no primeiro chat.
